# Правила обработки заметок

## 1. Какие файлы сервис видит

Сервис обходит все файлы с расширением `.md` внутри `/data` рекурсивно.

Не обрабатываются особым образом:

- не-Markdown файлы;
- файлы внутри каталогов `.trash`;
- файлы, изменённые менее 5 минут назад.

## 2. Что считается заметкой-предметом

Заметка считается предметом, если во фронтматтере есть:

```yaml
item: true
```

Проверка реализована небуквально:

- значение приводится к строке;
- затем к нижнему регистру;
- затем сравнивается с `"true"`.

Это значит, что будут считаться истинными, например:

- `true`
- `"true"`
- `TRUE`

## 3. Что считается контейнером вещей

Файл считается вложенным в контейнер вещей, если его родительская папка описана одноимённой заметкой с `item: true`.

Пример:

```text
Пригородная 26/
  Комната/
    Шкаф/
      Шкаф.md
      Куртка.md
```

Если в `Шкаф.md` есть `item: true`, то `Куртка.md` считается лежащей в контейнере вещей.

Если одноимённой заметки нет или в ней `item` не равен `true`, дочерние файлы не участвуют в расчёте `path`.

## 4. Как обновляется поле `path` и ссылка на место хранения

Поле `path` и первая строка тела заметки корректируются только для тех заметок, которые одновременно:

- находятся внутри контейнера вещей;
- сами имеют `item: true`.

Значение строится как цепочка всех папок-контейнеров от корня `/data` до родительской папки файла.

Пример:

```text
/data/Пригородная 26/Сарайка у папы/Коробка КБ2/Деталь.md
```

даёт:

```yaml
path: Сарайка у папы/Коробка КБ2
```

После фронтматтера первой строкой тела должна идти Markdown-ссылка на файл заметки последнего контейнера хранения.
Это не ссылка на папку: Obsidian открывает именно `.md`-файл, который лежит в этой папке и называется так же, как папка.
В самой заметке контейнера, например `Коробка КБ2/Коробка КБ2.md`, ссылка на саму себя не добавляется.

Для примера выше целевой файл:

```text
/data/Пригородная 26/Сарайка у папы/Коробка КБ2/Коробка КБ2.md
```

Ожидаемая первая строка тела:

```md
[Коробка КБ2](Коробка%20КБ2.md)
```

Если первая строка уже содержит правильную ссылку, она не меняется.
Если первой строкой стоит другая локальная Markdown-ссылка на `.md`-файл, она заменяется.
Если первой строкой идёт обычный контент, картинка или пустое тело, правильная ссылка вставляется перед этим содержимым.
Ссылки и любой другой контент ниже первой строки тела сервис не трогает.

Если `path` и первая ссылка уже совпадают с вычисленными значениями, файл не переписывается.

## 5. Список содержимого в заметке места хранения

Заметка места хранения — это `.md`-файл, имя которого совпадает с именем родительской папки и у которого во фронтматтере указано `item: true`. Например, `Ряд 1/Ряд 1.md`.

Для такой заметки сервис поддерживает управляемый список ссылок самым первым блоком тела:

- список собирается из непосредственного содержимого папки;
- сама заметка места хранения в список не попадает;
- из подпапок в список попадает только одноимённая заметка подпапки и только если эта подпапка тоже является местом хранения;
- остальные файлы из подпапок не попадают;
- файлы внутри `.trash` и не-Markdown файлы не попадают;
- сортировка: сначала обычные `.md`-файлы первого уровня, потом подпапки-контейнеры; внутри каждой группы — по имени без учёта регистра.

Формат:

- текст ссылки — имя файла без `.md`;
- target кодируется так же, как и одиночная ссылка на место хранения (пробелы и небезопасный ASCII через `%XX`, кириллица и Unicode остаются читаемыми, слэш между папкой и одноимённым файлом не кодируется).

Управляемый список отделён от ручного контента одной пустой строкой. Управляемым считается только начальный блок подряд идущих Markdown-ссылок на `.md`. Всё, что идёт после первой пустой строки или после первой не-ссылочной строки тела, считается ручным контентом и не меняется.

Если фактический начальный блок совпадает с ожидаемым, файл не переписывается.

## 6. Как обновляются даты

Логика обновления `creation_date` и `modification_date` в коде есть, но в рабочем цикле сейчас отключена.

Если её включить:

- формат даты будет `ДД.ММ.ГГГГ ЧЧ:ММ:СС`;
- `creation_date` берётся из `ctime`, а если он недоступен, из `mtime`;
- `modification_date` берётся из `mtime`;
- после записи сервис восстанавливает исходный `mtime`, чтобы не провоцировать бесконечные обновления.

## 7. Какие файлы удаляются

Сервис удаляет Markdown-файлы, если:

- имя файла начинается с `Без названия`;
- файл не находится в корне `/data`;
- файл не находится внутри `.trash`;
- файл старше 5 минут.

Примеры имён, подпадающих под правило:

- `Без названия.md`
- `Без названия 2.md`

В режиме `FAKE_FILE_WORKING=true` удаление не выполняется физически.

## 8. Требования к фронтматтеру

Безопасная запись работает только для файлов, которые:

- начинаются с первой строки `---`;
- имеют закрывающую строку `---`;
- содержат YAML mapping между разделителями.

Если фронтматтер повреждён, сервис не должен молча переписывать файл. Он завершит обработку этого файла с ошибкой в логах.

## 9. Правила безопасной записи

При изменении фронтматтера сервис обязан:

- сначала полностью прочитать файл;
- полностью провалидировать структуру;
- только потом писать изменения;
- сохранять исходный стиль переводов строк;
- сохранять BOM, если он был;
- при ошибке записи попытаться вернуть исходное содержимое.

Это одно из главных инвариантов проекта. При доработках нельзя упрощать запись до схемы "открыли файл и переписали вслепую".

## 10. Наблюдаемые ограничения

- Путь рассчитывается только для тех веток, где папки соответствуют файловой конвенции контейнера вещей.
- Фронтматтер читается только в первой YAML-секции файла. Из тела анализируется только первая строка после фронтматтера.
- Обход использует `os.walk`, поэтому большие каталоги будут сканироваться полностью на каждом цикле.

## 11. Что важно не сломать при развитии проекта

- Режим `FAKE_FILE_WORKING` должен покрывать все операции записи и удаления.
- Исключение `.trash` должно сохраняться, если бизнес-правило не меняется явно.
- Cooldown в 5 минут защищает от гонок с ручным редактированием и должен пересматриваться осознанно.
- Документация должна обновляться вместе с изменением файловых конвенций.
